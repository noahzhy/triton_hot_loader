# 【提测】Triton Hot Loader Controller 缺陷修复

## 提测版本

- 镜像：`ccr.ccs.tencentyun.com/clobotics/triton-hot-loader:20260824-181329`

## 新增环境变量配置

以下环境变量必须配置在 `test/realtime` Deployment 的 `triton-controller` 容器中；本仓库的 `deploy/realtime-dev/trtis-deployment-realtime-dev.yaml` 已包含相同配置。

```yaml
- name: TRITON_RELOAD_MAX_ATTEMPTS
  value: "8"
- name: TRITON_RELOAD_RETRY_BASE_SECONDS
  value: "2"
- name: TRITON_RELOAD_RETRY_MAX_SECONDS
  value: "60"
- name: TRITON_RELOAD_TIMEOUT_SECONDS
  value: "600"
```

- `TRITON_RELOAD_MAX_ATTEMPTS`：对同一 operation 最多发起的 Triton load/reload 次数。
- `TRITON_RELOAD_RETRY_BASE_SECONDS`：首次重试等待秒数；后续按指数退避增长。
- `TRITON_RELOAD_RETRY_MAX_SECONDS`：单次退避等待上限。
- `TRITON_RELOAD_TIMEOUT_SECONDS`：从首次 Triton load 起等待目标版本 READY 的总时限。

上述是本次提测推荐值。若环境有更严格的变更窗口，可在提测前调整，但需保证 `TRITON_RELOAD_RETRY_MAX_SECONDS >= TRITON_RELOAD_RETRY_BASE_SECONDS`，且各值均为正数。

## 本轮改进

1. 修复多版本模型 READY 误判
   - 每个 model-copy Job 记录本次交付的目标版本；READY 判断只接受目标版本，完整遍历 Triton repository index。
   - 当旧版本为 `UNAVAILABLE`、新版本为 `READY` 时，当前 Job 应直接进入 `MODEL_READY`，不再被旧版本阻塞或继续 reload。

2. 防止重复请求和状态串扰
   - 同一 `model_name + image` 的活跃重复 load 复用同一个 Job/operation，不重复创建 copy Job。
   - 同一模型在活跃 operation 期间提交不同镜像时返回 HTTP `409`。
   - 已经失败的历史 Job 保持 `TRITON_RELOAD_FAILED`，不会因后续其他版本 READY 被改写为成功。

3. 为 reload 加入受控重试
   - 使用持久化指数退避，默认最多 `8` 次、起始 `2s`、最大间隔 `60s`、总时限 `600s`。
   - Job 状态增加 `target_versions`、`triton_reload_attempts`、`triton_reload_last_attempt_at`、`triton_reload_next_attempt_at` 和 `error`。
   - 达到次数或总时限后进入明确终态 `TRITON_RELOAD_FAILED`，不再无限 reload。

4. 明确 unload/reload 的可恢复语义
   - `unload` 只卸载 Triton 运行态，保留 PVC 模型文件和 controller 镜像映射。
   - `reload` 可直接重新 load 同一模型，不创建 copy Job、不要求再次提供原始镜像。
